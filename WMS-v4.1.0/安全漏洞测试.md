## 二、详细漏洞（24 项，按危险程度排序）

**测试条件**：不安装任何第三方扫描器，仅用本机已有的 `curl`、MySQL CLI、`npm audit` 完成。  
第一轮覆盖接口 / 鉴权 / 前端表层，第二轮重点验证「工具扫不出来、但业务上最致命」的一类问题：状态机、重复提交、参数篡改、越权归属。  
下面 24 项按危险程度排列，**编号即排名**（01 最严重），不再区分轮次。

### SEC-01 缺少角色鉴权（严重）✅ 已修复

**问题**  
拦截器只校验"有没有合法 token"，从不校验"这个角色能不能调这个接口"。  
`AuthInterceptor` 把角色放进了 `request.setAttribute("loginRole", ...)`，但**全项目没有任何地方读取它**：

```java
// AuthInterceptor.java:43-44
request.setAttribute("loginUser", username);
request.setAttribute("loginRole", tokenService.resolveRole(token)); // 设了，但没人用
```

而前端是按角色隐藏菜单的（`meta.roles`），所以**界面上的权限控制完全是"装饰"**。

**复现**

```bash
# 用最低权限的拣货员登录
PT=$(curl -s -X POST http://127.0.0.1:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"picker","password":"123456"}' | sed -E 's/.*"token":"([^"]+)".*/\1/')

# 访问管理员专属接口
curl -H "Authorization: Bearer $PT" http://127.0.0.1:8080/api/base/employee/page
curl -H "Authorization: Bearer $PT" http://127.0.0.1:8080/api/log/page
curl -H "Authorization: Bearer $PT" http://127.0.0.1:8080/api/analytics/overview
```

**实测结果**

```
200 code=0  /api/base/employee/page     ← 全量员工档案（工号/姓名/班组/角色）
200 code=0  /api/log/page               ← 全量操作审计日志
200 code=0  /api/base/sku/page          ← 商品与成本价
200 code=0  /api/analytics/overview     ← 经营分析数据
```

同样地，拣货员还能调用 `POST /api/wave/generate`（生成波次）、`POST /api/order/pool-all`（一键汇聚全部订单）、  
`POST /api/wave/{waveNo}/cancel`（取消波次）等写操作。

**影响**

- 垂直越权：低权限角色获得管理员全部能力；
- 数据泄露：员工档案、操作日志、成本价、经营指标全量可读；
- 业务破坏：可批量改订单/波次状态，且日志里操作人是真实账号，事后追责困难。

**修复建议**

1. 在拦截器里做统一鉴权（推荐，集中且不易漏）：

```java
// 1) 给接口打注解
@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface RequireRole { String[] value(); }

// 2) 拦截器里校验
HandlerMethod hm = (HandlerMethod) handler;
RequireRole rr = hm.getMethodAnnotation(RequireRole.class);
if (rr != null) {
    String role = (String) request.getAttribute("loginRole");
    if (Arrays.stream(rr.value()).noneMatch(r -> r.equals(role))) {
        writeForbidden(response, "没有该操作权限");   // 403
        return false;
    }
}

// 3) 使用
@RequireRole({"ADMIN", "WAVE_OPERATOR"})
@PostMapping("/generate") ...
```

1. 权限矩阵建议：

| 模块         | ADMIN | WAVE_OPERATOR | PICKER | REVIEWER |
| ---------- | ----- | ------------- | ------ | -------- |
| 订单汇聚/取消    | ✓     | ✓             | ✗      | ✗        |
| 波次生成/指派/关闭 | ✓     | ✓             | ✗      | ✗        |
| 拣货执行       | ✓     | ✓             | ✓      | ✗        |
| 缺货处理       | ✓     | ✓             | ✓（仅上报） | ✗        |
| 复核/交接      | ✓     | ✗             | ✗      | ✓        |
| 基础数据/日志/分析 | ✓     | 只读            | ✗      | 只读       |

### SEC-02 密码可逆存储 + 接受 Base64 密码（高）✅ 已修复

**问题**  
`sys_user.password` 存的是 `MTIzNDU2`，即 `123456` 的 Base64。Base64 是编码不是加密，**任何人都能直接还原**。  
更糟的是登录接口同时接受明文和 Base64 两种形式：

```java
// AuthController.java:47-50
String base64 = Base64.getEncoder().encodeToString(input.getBytes(UTF_8));
if (!stored.equals(input) && !stored.equals(base64)) { throw ... }
```

**复现**

```bash
# 明文登录成功
curl -X POST http://127.0.0.1:8080/api/auth/login \
  -H "Content-Type: application/json" -d '{"username":"admin","password":"123456"}'

# 直接把数据库里的值当密码提交，同样成功
curl -X POST http://127.0.0.1:8080/api/auth/login \
  -H "Content-Type: application/json" -d '{"username":"admin","password":"MTIzNDU2"}'
```

**实测结果**

```sql
mysql> select username,password from wms_v4.sys_user;
admin     MTIzNDU2      -- = 123456
wave      MTIzNDU2
picker    MTIzNDU2
reviewer  MTIzNDU2
```

两条登录请求都返回 `code:0` 并签发 token。

**影响**  
一旦数据库被拖库（SQL 注入、备份泄露、运维误操作），攻击者可**瞬间还原所有明文密码**；  
由于员工普遍复用密码，会横向危及邮箱、VPN 等外部系统。

**修复建议**

```java
// 引入 spring-security-crypto（只需这一个依赖，不必上整套 Security）
BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();

// 登录
if (!encoder.matches(req.getPassword(), stored)) { throw new IllegalArgumentException("账号或密码错误"); }

// 初始化/改密
String hash = encoder.encode(rawPassword);   // $2a$10$...
```

同时：

- 删除"同时接受明文和 Base64"的兼容分支，只保留一种校验；
- 首次登录强制改密；
- 密码策略：长度 ≥ 8，禁止与用户名相同，禁止纯数字。

### SEC-03 登录无失败锁定/限流（高）

**问题**  
`/api/auth/login` 没有任何计数、锁定、验证码或延迟机制。

**复现**

```bash
for i in $(seq 1 8); do
  curl -s -X POST http://127.0.0.1:8080/api/auth/login \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"admin\",\"password\":\"wrong$i\"}"
done
```

**实测结果**

```
第1次 http=200 msg=账号或密码错误
...
第8次 http=200 msg=账号或密码错误     ← 无锁定、无延迟、无验证码
```

**影响**  
配合 SEC-02（密码仅 6 位纯数字、且账号名可从登录页直接看到），  
**离线字典 10 万次以内即可命中**；实测单次登录约 4ms（`time_total` 0.0035~0.0045s），  
单线程一小时可尝试约 90 万次，多线程并发可达千万级。

**修复建议**

- 单账号 5 次失败锁定 15 分钟，或指数退避（1s/2s/4s…）；
- 按 IP + 账号双维度限流（Bucket4j / Redis 计数器）；
- 失败次数记入 `operation_log`，便于告警；
- 生产环境加图形/滑块验证码。

### SEC-04 CORS 任意 Origin + 允许携带凭证（高）

**问题**

```java
// WebConfig.java:19-24
registry.addMapping("/api/**")
        .allowedOriginPatterns("*")     // 反射任意 Origin
        .allowCredentials(true)         // 且允许带 cookie/凭证
```

**复现**

```bash
curl -D - -o /dev/null -H "Origin: https://evil.example.com" \
  -H "Authorization: Bearer $T" \
  "http://127.0.0.1:8080/api/order/page?pageSize=1"

curl -D - -o /dev/null -X OPTIONS \
  -H "Origin: https://evil.example.com" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization" \
  "http://127.0.0.1:8080/api/wave/generate"
```


**实测结果**

```
Access-Control-Allow-Origin: https://evil.example.com     ← 原样反射
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS
Access-Control-Allow-Headers: authorization
Access-Control-Max-Age: 3600
```

**影响**  
任意站点都能在受害者浏览器里跨域调用本系统接口。当前 token 放在 `Authorization` 头（非 Cookie），  
所以攻击者拿不到 token 就发不出带身份的请求，**危害被削弱但未消除**：

- 一旦将来把 token 改成 Cookie（很常见的演进），立刻升级为可越权读写的 CSRF；
- 现在也可用于跨域探测系统是否存在、枚举接口、探测版本。

**修复建议**

```java
registry.addMapping("/api/**")
        .allowedOrigins("http://127.0.0.1:5173", "https://wms.your-domain.com")
        .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
        .allowedHeaders("Content-Type", "Authorization")
        .allowCredentials(true)
        .maxAge(3600);
```



生产环境用环境变量注入白名单，不要写死也不要用 `*`。

### SEC-05 复核单可重复提交，覆盖已完成结果（高）✅ 已修复

**问题**  
`ReviewController#submit` 只按 `reviewNo` 查单，**不校验当前状态**，也不校验复核单是否已被认领。

**复现**

```bash
# 对一张已经 PASS 的复核单再次提交，并把实际数量改成 1
curl -X POST http://127.0.0.1:8080/api/review/submit \
  -H "Authorization: Bearer $T" -H "Content-Type: application/json" \
  -d '{"reviewNo":"RV202610160018","actualQty":1}'
```

**实测结果**

```
提交前： PASS  2026-10-13 09:24:55  actual_qty=4
提交后： PASS  2026-10-20 02:25:35  actual_qty=1     ← 结果被覆盖
```

**影响**

- 已完成的质量门禁可被任意重写，`PASS` 与 `actual_qty` 自相矛盾（应判 DIFF 却仍是 PASS）；
- 复核时长 `duration_sec` 被重算，绩效考核数据失真；
- 可反复提交刷出"零差异"记录，掩盖错发、少发。

**修复建议**  
只允许 `PENDING/REVIEWING` 状态提交，且校验认领人：

```java
String status = Repo.str(r.get("status"));
if (!"PENDING".equals(status) && !"REVIEWING".equals(status))
    throw new IllegalStateException("复核单当前状态（" + Dict.desc("reviewStatus", status) + "）不可提交");
if (!Objects.equals(reviewerNo, Repo.str(r.get("reviewerNo")))
    throw new IllegalStateException("该复核单不属于当前用户");
```

### SEC-06 交接单可重复确认，覆盖交接数据（高）✅ 已修复

**复现**

```bash
curl -X POST http://127.0.0.1:8080/api/handover/confirm \
  -H "Authorization: Bearer $T" -H "Content-Type: application/json" \
  -d '{"handoverNo":"HO20261012003","receiveName":"张三","actualPackageCount":1}'
```

**实测结果**

```
确认前： CONFIRMED  2026-10-12 09:41:37  package_count=7
确认后： CONFIRMED  2026-10-20 02:25:36  package_count=1  receive_name=张三
```

**影响**  
已完成的出库交接可被改写：件数从 7 改成 1、收货人可替换、交接时间被覆盖。  
一旦发生丢件纠纷，纸质/系统记录与实物对不上，责任无法界定。

**修复建议**  
`confirm` 前校验 `status='PENDING'`；已确认的只允许"撤销"（单独的、带审批的逆向操作），不允许原地覆盖。

### SEC-07 拣货任务可状态回退、可跳过开始直接完成（高）✅ 已修复

**问题**  
`start` 与 `finish` 都不校验前置状态。

**复现 A：已完成的任务重新开始**

```bash
curl -X POST "http://127.0.0.1:8080/api/pick/PK20261010001/start?pickerNo=P001" \
  -H "Authorization: Bearer $T"
```

```
执行前： FINISHED  start=2026-10-10 09:05:00  finish=2026-10-10 09:21:13
执行后： PICKING   start=2026-10-20 02:25:48  finish=2026-10-10 09:21:13   ← 状态倒退，且 finish < start
```

**复现 B：未开始的任务直接完成**

```bash
curl -X POST "http://127.0.0.1:8080/api/pick/PK20261016007/finish" -H "Authorization: Bearer $T"
```

```
执行前： WAITING  start=NULL
执行后： FINISHED start=NULL  finish=2026-10-20 02:25:49  duration=0
```

同时该波次被置为 `PICKED`、波次下订单被置为 `PICKED`。

**影响**

- 可凭空"完成"拣货，跳过实际作业，下游复核/交接照常流转 → 整条链路的数据全部失真；
- 状态可倒退，已完成的工时被清零重算，可用来刷绩效；
- 产生 `finish_time < start_time`、`duration=0` 这类脏数据，统计口径全部失效。

**修复建议**  
按状态机白名单推进，禁止跨状态跳转：

```java
// start: 只允许 WAITING
if (!"WAITING".equals(status)) throw new IllegalStateException("任务当前状态不可开始");
// finish: 只允许 PICKING，且必须所有明细已确认
if (!"PICKING".equals(status)) throw new IllegalStateException("任务尚未开始，不能完成");
long pending = jdbc.queryForObject("SELECT COUNT(*) FROM pick_item WHERE task_no=? AND status='PENDING'", Long.class, taskNo);
if (pending > 0) throw new IllegalStateException("还有 " + pending + " 条明细未确认");
```

### SEC-08 操作人由请求参数决定，可冒名（高）✅ 已修复

**问题**  
`start` 的 `pickerNo`、`review/submit` 的 `reviewerNo`、`reviewerName` 全部取自请求参数，  
服务端不校验"当前登录人是否就是这个工号"。

**复现**

```bash
# 登录人是 admin，却可以把任务挂到 P001 名下
```

**影响**

工号只从 token 上下文取，请求参数一律忽略：

```java
String pickerNo = (String) request.getAttribute("loginUser");
```

### SEC-09 异常信息回显 SQL 与框架细节（中）✅ 已修复（随 SEC-18 一并解决）

**问题**

```java
// GlobalExceptionHandler.java:29-33
@ExceptionHandler(Exception.class)
public ApiResult<Void> handleException(Exception e) {
    log.error("系统异常", e);
    return ApiResult.fail("系统异常：" + e.getMessage());   // 把内部信息直接返回给调用方
}
```

**复现**

```bash
# 负页码 → OFFSET 为负 → SQL 语法错误
curl -H "Authorization: Bearer $T" \
  "http://127.0.0.1:8080/api/order/page?pageNum=-1&pageSize=10"
```

**实测结果**

```json
{
  "code": 1,
  "message": "系统异常：PreparedStatementCallback; bad SQL grammar [SELECT * FROM `order` WHERE 1=1 ORDER BY CASE priority WHEN 'URGENT' THEN 0 ELSE 1 END, pay_time DESC, id DESC LIMIT 10 OFFSET -20]"
}
```

一次请求就泄露了：表名、字段名、排序逻辑、分页实现、以及底层用的是 JdbcTemplate。  
另外畸形 JSON 会返回 `JSON parse error: Unexpected end-of-input ...`（框架版本特征）。

**影响**  
为后续 SQL 注入、越权查询提供精确的schema情报；也暴露技术栈版本，便于匹配已知 CVE。

**修复建议**

- 对外统一返回模糊文案（"系统繁忙，请稍后重试"），错误 ID 返回给用户，详情只进日志：

```java
String traceId = UUID.randomUUID().toString();
log.error("系统异常 traceId={}", traceId, e);
return ApiResult.fail("系统繁忙，请稍后重试（错误码 " + traceId + "）");
```

- 分页参数在入口处收敛：`pageNum = Math.max(1, pageNum)`，`pageSize` 限制 1~200。

### SEC-10 缺失安全响应头（中）

**复现**

```bash
curl -D - -o /dev/null http://127.0.0.1:8080/api/order/page
curl -D - -o /dev/null http://127.0.0.1:5173/
```

**实测结果**  
后端与前端响应里**都没有**下列头：

| 头                                | 作用                   | 现状 |
| --------------------------------- | ---------------------- | ---- |
| `X-Content-Type-Options: nosniff` | 阻止 MIME 嗅探         | 缺失 |
| `X-Frame-Options: DENY`           | 防点击劫持             | 缺失 |
| `Content-Security-Policy`         | 限制脚本来源，兜底 XSS | 缺失 |
| `Referrer-Policy`                 | 防 Referer 泄露        | 缺失 |
| `Strict-Transport-Security`       | 强制 HTTPS             | 缺失 |
| `Cache-Control: no-store`         | 防敏感响应被缓存       | 缺失 |

`index.html` 里也没有 CSP meta。

**影响**

- 可被 iframe 嵌套做点击劫持（诱导管理员点"取消波次"等按钮）；
- 一旦出现 XSS，没有 CSP 兜底；
- 响应可能被中间代理/浏览器缓存。

**修复建议**

后端加一个 Filter：

```java
response.setHeader("X-Content-Type-Options", "nosniff");
response.setHeader("X-Frame-Options", "DENY");
response.setHeader("Referrer-Policy", "no-referrer");
response.setHeader("Content-Security-Policy",
    "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; frame-ancestors 'none'");
```

若用 Nginx 托管前端，在 `server` 块统一 `add_header`。

### SEC-11 Token 无法吊销、无登出接口（中）

**问题**  
`TokenService` 只在内存 Map 里记 token，没有 `logout` 接口；前端"退出登录"只是清掉本地 localStorage，  
**服务端 token 依然有效**。

**复现**

```bash
curl -X POST -H "Authorization: Bearer $T" http://127.0.0.1:8080/api/auth/logout
```

**实测结果**

```json
{"code":1,"message":"系统异常：No static resource api/auth/logout for request '/api/auth/logout'."}
```

即接口不存在。同时 token 内容可直接解出：

```
$ echo "$T" | base64 -d
A001:26b5d2b9-4d18-4d99-b537-a93e93ba37f3:1792462755585:ADMIN
```

**影响**

- 员工离职、设备丢失、token 泄露后，8 小时内无法强制下线；
- 明文暴露工号、角色、过期时间（信息收集成本降低）；
- 服务重启后所有 token 失效（可用性问题，非安全问题，但需知晓）。

**修复建议**

- 增加 `POST /api/auth/logout`，调用 `tokenService.remove(token)`；
- 前端退出时先调接口再清本地；
- 中长期改为 JWT + 短有效期（15min）+ Refresh Token，或服务端 Session + Redis；
- token 里不要放角色明文，改为服务端查库/缓存。

### SEC-17 分页与请求体无上限（低）

**实测**

```bash
pageSize=10      → 15ms  10KB
pageSize=10000   → 52ms  68KB
```

### SEC-18 不存在的路径返回 HTTP 200（低）✅ 已修复

**实测**


```bash
curl -H "Authorization: Bearer $T" http://127.0.0.1:8080/api/not-exist
```

```json
{"code":1,"message":"系统异常：No static resource api/not-exist for request '/api/not-exist'."}
```

HTTP 状态码是 **200**，而不是 404。同理 `/actuator`、`/swagger-ui.html` 也返回 200 + 类似文案。

**影响**

- 监控与网关无法按状态码识别异常；
- 攻击者可通过文案差异判断路由是否存在；
- 暴露 Spring 静态资源处理细节。

**修复建议**

- 404 返回 404，403 返回 403，401 返回 401；
- 未匹配路由统一走 `ErrorController`，返回固定文案。

**修复后（2026-10-20）**

`GlobalExceptionHandler` 里补了三个分支，把「协议错误」和「业务错误」分开：

| 异常                                                             | 状态码  | 响应体                                               |
| ---------------------------------------------------------------- | ------- | ---------------------------------------------------- |
| `NoResourceFoundException` / `NoHandlerFoundException`           | 404     | `{"code":1,"message":"接口不存在"}`                  |
| `HttpRequestMethodNotSupportedException`                         | 405     | `"不支持的请求方法：GET"`                            |
| `MethodArgumentTypeMismatch` / 缺参 / JSON 解析失败              | 400     | `"请求参数不合法，请检查后重试"`                     |
| 其他未预期异常                                                   | 500     | `"系统异常，请稍后重试或联系管理员"`（堆栈只进日志） |
| 业务异常（`IllegalArgumentException` / `IllegalStateException`） | **200** | `code=1` + 具体文案（前端契约不变）                  |

`/actuator`、`/swagger-ui.html` 这类静态兜底路径也走 404，不再吐「No static resource api/xxx」。

| **部署**       | SEC-21                   | TLS + HSTS + 网关限流                                                                                      | 视环境     |

### 4.2 三个关键改造的落地要点

**① 角色鉴权（SEC-01 + SEC-08 一起做）**

```java
// 1) 注解
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequireRole { String[] value(); }

// 2) 拦截器在 preHandle 里读 AuthInterceptor 已放入的角色
RequireRole rr = handlerMethod.getMethodAnnotation(RequireRole.class);
if (rr != null) {
    String role = (String) request.getAttribute("loginRole");
    if (Arrays.stream(rr.value()).noneMatch(r -> r.equalsIgnoreCase(role))) {
        response.setStatus(403);
        // 统一响应体 { code: 403, message: "无权限" }
        return false;
    }
}

// 3) Controller 里操作人不再来自请求参数
String operator = (String) request.getAttribute("loginEmployeeNo");
```

权限矩阵建议：

| 接口族                                | ADMIN | WAVE | PICKER | REVIEWER |
| ------------------------------------- | :---: | :--: | :----: | :------: |
| `/api/base/**`（员工/商品/库位/字典） | ✔     | —    | —      | —        |
| `/api/order/**` 读写                  | ✔     | ✔    | —      | —        |
| `/api/wave/**` 生成/分配              | ✔     | ✔    | —      | —        |
| `/api/pick/**` 执行                   | ✔     | —    | ✔      | —        |
| `/api/review/**` 复核                 | ✔     | —    | —      | ✔        |
| `/api/stats/**`、`/api/log/**`        | ✔     | —    | —      | —        |

**② 单据状态机（SEC-05 / SEC-06 / SEC-07）**

在三处写入前加同一段守卫，禁止"已终态再写"和"跳步"：

```java
private void assertStatus(String current, String... allowed) {
    if (Arrays.stream(allowed).noneMatch(current::equals)) {
        throw new BizException("单据状态不允许该操作，当前状态：" + current);
    }
}
// 复核：assertStatus(status, "PENDING");
// 交接：assertStatus(status, "PENDING");   // CONFIRMED 直接拒绝
// 开始拣货：assertStatus(status, "WAITING");
// 完成拣货：assertStatus(status, "PICKING");  // 不允许 WAITING 直接 FINISHED
```

配合数据库兜底，防止并发绕过：

```sql
UPDATE review SET status='PASS' WHERE review_no=? AND status='PENDING';
-- 影响行数 = 0 即视为已被处理，返回"该复核单已处理"
```

**③ 终态不可回退（SEC-07 后半段）**

当前 `start` 会把 `FINISHED` 改回 `PICKING` 并清空 `finish_time`，属于审计破坏。  
除状态守卫外，建议给 `pick_task` 加 `version` 字段做乐观锁，并在 `operation_log` 里记录 `before_status → after_status`。
