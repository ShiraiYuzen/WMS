## 三、SEC-01 角色鉴权

### 3.1 设计

原先 `AuthInterceptor` 只判断"token 是否合法"，把角色塞进 `request.setAttribute("loginRole")` 后  
**全项目没有任何地方读取它**，等于所有登录用户共享最高权限。

修复后分三层：

1. **认证**：token 必须存在于服务端会话表 → 否则 401；
2. **上下文**：登录人写入 `AuthContext`，Controller 从上下文取工号，不再信请求参数；
3. **授权**：拦截器读 `@RequireRole`，不匹配 → 403，并在响应体里说明当前角色。

```java
// AuthInterceptor#preHandle（节选）
LoginUser user = session.user();
AuthContext.set(user);

if (!hasPermission(handler, user)) {
    AuthContext.clear();
    writeError(response, 403, 403, "当前角色（" + roleText(user.role()) + "）无权执行该操作");
    return false;
}

private boolean hasPermission(Object handler, LoginUser user) {
    if (!(handler instanceof HandlerMethod hm)) return true;
    RequireRole rr = hm.getMethodAnnotation(RequireRole.class);   // 方法优先
    if (rr == null) rr = hm.getBeanType().getAnnotation(RequireRole.class); // 再看类
    return rr == null || user.hasRole(rr.value());                // 未标注 = 登录即可
}
```

用法：

```java
@RequireRole({"ADMIN", "WAVE_OPERATOR"})
@PostMapping("/generate")
public ApiResult<...> generate(...) { ... }
```

| `/api/wave/**`                                          | 登录即可  | ADMIN、WAVE_OPERATOR        | 预览、生成、指派、归档、取消               |

## 四、SEC-02 口令散列

### 4.1 算法选择

**结论：BCrypt，cost = 10（每次校验约 50~100ms），由 `spring-security-crypto` 提供。**

> 演进过程：第一版为了"零新增依赖"用了 JDK 自带的 PBKDF2（21 万次迭代）；  
> 后来确认可以联网拉取依赖，改为报告原本建议的 BCrypt。PBKDF2 的校验代码保留下来做**向下兼容**，  
> 老数据登录一次就自动升级，不会把任何人锁在门外。

为什么是 BCrypt：

- 自带盐，不需要额外管理 salt 字段；
- 内存访问模式对 GPU / ASIC 不友好，离线爆破成本高于 PBKDF2；
- `spring-security-crypto` 只依赖 `spring-core`（项目已有），jar 约 80KB，  
  **不引入整个 Spring Security 框架**，不加任何 Filter、不改任何接口签名。

```xml

<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-crypto</artifactId>
</dependency>
```

版本由 `spring-boot-dependencies:4.1.1` 统一管理（当前解析到 7.1.1），不写死版本号。

### 4.2 存储格式

```
$2a$10$GXyebhUCt7l55jcb6AGuJeDv9/BBGEEmROd.JG/ncsjcCAF9DZ3Ge
 │   │  └── 22 字符盐 + 31 字符散列（同一口令每次结果都不同）
 │   └── cost（2^10 轮）
 └── 算法版本
```

`sys_user.password` 是 `VARCHAR(128)`，BCrypt 固定 60 字符，够用且留了升级余量。

### 4.3 三种格式的兼容策略

| 格式                | 示例                | 登录时                   | 处理方式                             |
| ----------------- | ----------------- | --------------------- | -------------------------------- |
| BCrypt            | `$2a$10$…`        | 直接校验                  | 当前标准                             |
| PBKDF2（v1 过渡版）    | `pbkdf2$210000$…` | 校验通过后**立即改写为 BCrypt** | `AuthController` 里无感升级           |
| 明文 / Base64（历史遗留） | `MTIzNDU2`        | **拒绝**                | 启动时由 `DatabaseInitializer` 一次性迁移 |

登录流程只认前两种，明文/Base64 一律不通过——这是 SEC-02 的核心要求。

```java
// AuthController#login（节选）
String stored = u == null ? null : Repo.str(u.get("password"));
if (!PasswordHasher.matches(req.getPassword(), stored)) {
    throw new IllegalArgumentException("账号或密码错误");   // 与"用户不存在"同文案，防枚举
}
// 老散列无感升级为 BCrypt，用户不需要改密
if (PasswordHasher.needsUpgrade(stored)) {
    repo.jdbc().update("UPDATE sys_user SET password=? WHERE username=? AND password=?",
            PasswordHasher.hash(req.getPassword()), req.getUsername().trim(), stored);
}
```


`needsUpgrade()` 除了"不是 BCrypt"之外，还会在 **cost 被调低时**返回 true  
（`BCryptPasswordEncoder#upgradeEncoding`），将来把强度从 10 提到 12 也能平滑过渡。

### 4.4 启动时的一次性迁移

明文 / Base64 无法在登录时处理（登录已经拒绝了它们），所以在启动任务里迁移：

```java
// DatabaseInitializer#migrateLegacyPasswords（节选）
String plain = PasswordHasher.decodeLegacy(stored);   // BCrypt / PBKDF2 会返回 null
if (plain == null || plain.isBlank()) continue;
jdbc.update("UPDATE sys_user SET password=? WHERE id=? AND password=?",
            PasswordHasher.hash(plain), id, stored);   // 条件更新，幂等
```


`decodeLegacy` 的判定：先按 Base64 解，解出来全是可打印 ASCII 就认定"Base64 过的明文"，  
否则视为明文原样使用。`MTIzNDU2` 与 `123456` 两种历史写法都能无损迁移，不需要强制重置口令。

启动日志会逐条打印：

```
WARN  账号 plaintest 的口令已从明文/Base64 升级为 BCrypt 散列
WARN  共升级 1 条历史口令，请通知相关账号重新确认口令强度
```

### 4.5 时序与异常

- BCrypt 内部用定长比较；PBKDF2 兼容分支用 `MessageDigest.isEqual`，都不按字节短路。
- 散列串格式损坏时 `matches()` 返回 false，不把 `IllegalArgumentException` 抛到接口层。

## 五、SEC-08 操作人上下文

### 5.1 问题

原实现里"操作人"来自请求参数，调用方可以随便填：

```java
// 修复前：PickController#start
public ApiResult<...> start(@PathVariable String taskNo,
                            @RequestParam(required = false) String pickerNo) {
    if (pickerNo != null && !pickerNo.isBlank()) {
        repo.jdbc().update("UPDATE pick_task SET picker_no=?, ...", pickerNo, ...);  // 谁都能改成别人
    }
}
```

### 5.2 修复

`AuthContext` 由拦截器写入，Controller 只读不写：

```java
LoginUser me = AuthContext.require();          // 取不到直接抛错
repo.log("PICK", taskNo, "PICK_START", "开始拣货", me.employeeNo(), me.employeeName(), me.role(), null);
```

各业务点的取值规则：

| 场景                            | 规则                                                       |
| ------------------------------- | ---------------------------------------------------------- |
| 拣货开工（角色 = PICKER）       | `picker_no = 本人`，请求里的 `pickerNo` 直接忽略           |
| 拣货开工（ADMIN / WAVE 代操作） | 保留任务原指派，**不覆盖** `picker_no`；日志记录真实操作人 |
| 复核领取 / 提交                 | `reviewer_no = 本人`                                       |
| 交接创建 / 确认                 | `handover_user_no = 本人`                                  |
| 缺货上报 / 处理                 | `reporter_no` / `handler_no` = 本人                        |
| 波次生成 / 指派 / 归档 / 取消   | `creator_no` / `operator_no` = 本人                        |
| 订单汇聚 / 取消                 | 日志 `operator_no` = 本人                                  |

前端仍在传 `pickerNo`、`reviewerNo` 等参数（`api/index.js`），后端签名已不再接收，Spring 会忽略多余的 query 参数，  
所以**前端不需要同步改动**，行为自动变为"以 token 为准"。

## 六、SEC-05 / SEC-06 / SEC-07 状态机

### 6.1 状态迁移表

**拣货任务 `pick_task.status`**

| 动作                       | 允许的起始状态                      | 目标状态                                    |
| -------------------------- | ----------------------------------- | ------------------------------------------- |
| `start` 开工               | `WAITING`                           | `PICKING`                                   |
| `confirm-item` 确认明细    | `WAITING` / `PICKING` / `EXCEPTION` | 不变（改明细）                              |
| `report-shortage` 上报缺货 | `WAITING` / `PICKING` / `EXCEPTION` | `EXCEPTION`                                 |
| `finish` 结单              | `PICKING` / `EXCEPTION`             | `FINISHED`（无缺货）/ `EXCEPTION`（有缺货） |

**复核单 `review.status`**

| 动作          | 允许的起始状态 | 目标状态        |
| ------------- | -------------- | --------------- |
| `submit` 提交 | `WAITING`      | `PASS` / `DIFF` |

**交接单 `handover.status`**

| 动作                  | 允许的起始状态 | 目标状态                 |
| --------------------- | -------------- | ------------------------ |
| `confirm` 确认 / 拒收 | `CREATED`      | `CONFIRMED` / `REJECTED` |

### 6.2 两层防护

**第一层：先查后判，给出人话错误**

```java
private void assertStatus(Map<String, Object> task, String action, String... allowed) {
    String cur = Repo.str(task.get("status"));
    for (String a : allowed) if (a.equals(cur)) return;
    throw new IllegalStateException("任务当前状态为「" + Dict.desc("pickTaskStatus", cur) + "」，不能" + action);
}
```

**第二层：条件更新，防并发绕过**

即使两个请求同时通过第一层，也只有一条 SQL 能命中：

```java
int n = repo.jdbc().update(
    "UPDATE pick_task SET picker_no=?, picker_name=?, status='PICKING', start_time=? " +
    "WHERE task_no=? AND status='WAITING'", pickerNo, pickerName, now, taskNo);
if (n == 0) throw new IllegalStateException("该任务已被他人开始，请刷新后重试");
```

复核提交同理：

```java
int n = repo.jdbc().update("UPDATE review SET ... WHERE review_no=? AND status='WAITING'", ...);
if (n == 0) throw new IllegalStateException("该复核单已被其他人提交，请刷新后查看");
```

### 6.3 顺带修掉的连带问题

- **差异明细写入顺序**：原来先 `INSERT review_diff` 再更新主表，主表更新失败会留下孤儿差异行；  
  现在改为"主表条件更新成功后再写明细"。
- **波次状态同步**：`start` 里更新波次加了 `AND status IN ('CREATED','ASSIGNED')`，  
  避免一个已交接的波次被重新拉回 `PICKING`；`finish` 里加 `AND status='PICKING'`。
- **数量边界**：实拣不得大于应拣（多货走复核差异登记）；缺货必须落在 `1 ~ 未拣数量` 之间。
- **任务归属**：`assertOwnership()` 统一拦"拣货员操作他人任务"，`my-tasks` 与 `page` 对拣货员强制 `picker_no = 本人`。

## 十、回滚方法

改动集中在后端，回滚成本低：

```bash
# 1) 代码回滚到修复前（若已纳入 git）
git checkout -- backend/src/main/java/com/example/wms \
               backend/src/main/resources/schema.sql \
               frontend/src/router/index.js

# 2) 口令回滚（仅当需要恢复旧的 Base64 口令）
UPDATE sys_user SET password = 'MTIzNDU2' WHERE username IN ('admin','wave','picker','reviewer');

# 3) 重新打包启动
```

注意：第 2 步之后必须同时回滚 `AuthController`，否则旧格式口令无法登录。  
另外 `pom.xml` 里的 `spring-security-crypto` 也要一并去掉，并让 `PasswordHasher` 退回纯 PBKDF2 实现，  
否则会留下"依赖还在、却没人调用"的死代码。  
数据层面本轮没有做破坏性变更，`pick_task` / `review` / `handover` 的状态字段只是被规则约束，不需要回滚数据。

## 十一、补充修复：HTTP 状态码语义（SEC-09 / SEC-18 / SEC-22）

做 SEC-18 时发现根因是同一个：`GlobalExceptionHandler` 的兜底分支把所有异常都转成 **HTTP 200 + code=1**，
于是「路由不存在」「方法不对」「参数类型错」「SQL 报错」在网关和监控眼里全是成功。

### 11.1 改动

`config/GlobalExceptionHandler.java` 按异常类型分开处理：

| 异常                                                         | 状态码 | 文案                             |
| ------------------------------------------------------------ | ------ | -------------------------------- |
| `NoResourceFoundException`、`NoHandlerFoundException`        | 404    | 接口不存在                       |
| `HttpRequestMethodNotSupportedException`                     | 405    | 不支持的请求方法：GET            |
| `MethodArgumentTypeMismatchException`、缺参、请求体解析失败  | 400    | 请求参数不合法，请检查后重试     |
| 其他未预期异常                                               | 500    | 系统异常，请稍后重试或联系管理员 |
| `IllegalArgumentException` / `IllegalStateException`（业务） | 200    | 具体文案，前端契约不变           |

关键点：**业务失败仍然回 200 + code=1**。前端 `request.js` 是按 `res.code !== 0` 提示错误的，
如果业务失败也改成 4xx，得同步改 15 个页面的错误处理，收益不成正比。所以只把「协议层错误」改成真实状态码。

### 11.2 顺带解决的三项

- **SEC-09**：兜底分支不再回显 `e.getMessage()`，堆栈只进日志，SQL 片段不外泄；
- **SEC-18**：`/api/not-exist`、`/actuator`、`/swagger-ui.html` 从 200 变成 404，且不再吐 Spring 的「No static resource」；
- **SEC-22**：参数类型错从 200 变成 400。

### 11.3 复测

```text
正常请求   GET /api/dashboard/summary        HTTP 200  code=0
路由不存在 GET /api/not-exist                HTTP 404  接口不存在
静态兜底   GET /actuator                     HTTP 404  接口不存在
方法不对   GET /api/auth/login               HTTP 405  不支持的请求方法：GET
参数类型错 GET /api/order/page?pageNum=abc   HTTP 400  请求参数不合法
缺必填参数 GET /api/log/trace                HTTP 400  请求参数不合法
服务端错误 GET /api/order/page?pageNum=-1    HTTP 500  系统异常，请稍后重试或联系管理员
业务异常   POST /api/wave/assign 空 body     HTTP 200  code=1 缺少波次号或拣货员
```

回归：看板、缺货、波次等页面截图正常，无错误提示；401 / 403 行为未变。
